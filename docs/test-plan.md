# 测试与验收

已执行的双 Android 14 模拟器结果见 [模拟器实测](emulator-test.md)。下方的“真机”清单仍需真实手机执行。

## 自动检查

`signaling` 目录运行 `npm run check` 和 `npm test`。集成测试覆盖：

- 健康检查声明 TURN 关闭。
- 未确认的指导端不能转发 ICE，也不能冒充共享端确认。
- 管理凭据错误被拒绝；成功接受后原协助码失效。
- 拒绝指导端后，其关闭回调不误删共享端房间。
- 等待中的指导端退出，共享端仍可等待下一次申请。
- 录屏授权门槛、offer 发起方向、旧会话隔离及信令转发。
- 两个指导端并发加入时只选择一个等待申请。
- 猜码限流及畸形 JSON 不破坏房间对象。
- 累计信令延迟超过 30 秒时，已确认房间仍能完成媒体协商（35 秒实际延迟回归）。

测试中的 SDP/ICE 是协议占位字符串，只验证信令控制，**不验证媒体传输**。休眠恢复的结构已实现，但没有因普通集成测试通过就宣称实际发生了云端休眠。

Android 构建：`./scripts/build-android.ps1`。构建通过只证明依赖、源码和打包可完成，不代替设备运行。

Android 单元测试还覆盖媒体诊断：按 `transport.selectedCandidatePairId` 及候选 ID 找到实际路径；优先使用当前选中路径；发送和接收计数按角色区分；忽略音频统计；收到包或收到帧不冒充成功解码；输出不泄漏候选地址。这些测试使用统计数据夹具，不运行原生 WebRTC，也不验证实际手机编解码。

## 阶段 0 真机清单（待执行）

| 场景 | 期望 |
|---|---|
| 两机同网及不同网访问同一 WSS | 创建房间、加入申请、接受确认均成功 |
| 错误或已消费协助码 | 提示不可用，不泄漏其他房间 |
| 拒绝后再次申请 | 共享端原房间可继续使用，原有效期不延长 |
| 共享端结束、指导端断开或进程终止 | 对端结束，服务器清理房间 |
| 旋转配对页面 | 不创建第二个会话，已持有状态保留 |
| 断网 | 连接失败后恢复可操作状态，重新连接由用户发起 |
| WebRTC/STUN 检测 | 显示候选数量或失败说明，不请求采集权限 |
| 连续检测和离开页面 | 无明显原生资源泄漏或崩溃 |

## 后续阶段

阶段 1：系统授权、前台通知、本地预览、旋转、拒绝授权和多入口停止。Android 14+ 每次新会话重新授权，不重复创建同一投屏的虚拟显示。当前代码已实现，仍待真机执行下表。

阶段 2：同局域网两端持续变化的视频、等比显示、首次渲染、断开和幂等释放。当前 Android 协商代码已完成，仍待下表真机验收。

真机验收顺序：共享端和指导端安装同一个新 APK；双方加入并由共享端接受；共享端授权录屏；指导端应显示“正在建立视频连接”，随后出现“对方屏幕”。确认画面持续变化后，分别测试共享端停止、指导端断开、锁屏/系统停止投屏及断网。检查停止后通知消失、共享端不再采集，指导端渲染器释放；重新开始必须重新授权。

阶段 3：不同运营商 Wi-Fi、Wi-Fi/移动网络、移动网络/移动网络；验证 selected candidate pair、接收字节、解码帧及实际画面，不能仅凭 WSS 或 srflx 判断成功。

当前版本每三秒显示媒体统计。共享端的发送字节与编码帧、指导端的接收字节与解码帧都应随画面变化而增加；保持至少一分钟，并实际操作几个普通页面。待机的静态画面可能降低帧率，不作为失败依据。至少一帧被解码后才上报 `media.ready`，此前会话仍处于协商状态并受服务端超时约束。

| 观察 | 下一步排查 |
|---|---|
| 只有配对确认，尚未开始共享 | 共享端完成通知权限和本次系统录屏授权 |
| ICE 长时间未连接，随后失败 | 检查双方网络/STUN 可达性，先回同一 Wi-Fi 对照；公网可能需要 TURN |
| 共享端编码/发送不增长 | 排查投屏停止、受保护内容、采集和编码 |
| 发送增长，指导端接收不增长 | 排查 ICE 路径、UDP/NAT 或网络变化 |
| 接收增长但解码为零，或有解码但黑屏 | 排查编解码、渲染器及受保护页面；不能仅归因为缺少 TURN |
| 指导端画面持续变化且双方计数增长 | 该设备和该网络组合通过媒体验收；继续测试停止和断网 |

阶段 4：按实测失败原因决定是否评估 TURN；涉及可能计费的配置默认不启用。

阶段 5 已实现指导端单向语音。Debug 合成测试验证 Android 录音生命周期、Opus/WebRTC 传输、对端实际播放输出和停止；Release 不包含探针。真实手机的声音质量仍待验收。

## MVP 补充验收

| 场景 | 期望 |
|---|---|
| 只共享屏幕 | 两端不启动 AudioRecord，不请求麦克风 |
| 指导端拒绝麦克风 | 视频继续；没有 microphone 前台服务 |
| 允许并开启麦克风 | 录音通知出现；对端接收/播放声音，语音计数增长 |
| 应用内或通知栏关闭麦克风 | 实际 AudioRecord 停止、通知移除、视频继续 |
| 反复开启关闭语音 | 不重复绑定音轨或遗留录音；不需要重新配对 |
| 全屏、返回和指导端旋转 | 等比视频继续，音频状态与停止入口保留 |
| 任一端锁屏 | 双端结束，投屏和麦克风通知消失 |
| 任一端进程终止 | 对端结束，采集清理 |
| 实际媒体网络断开 | 超时结束采集；恢复网络不自动恢复共享 |
| 授权弹窗打开后远端退出 | 授权返回不启动新采集 |

自动回归：先 `emulator-smoke.py run`，再 `emulator-voice-test.py run`、`emulator-smoke.py suite`；各脚本操作同一模拟器，必须逐个完成，不能并发。MVP 生命周期脚本 `emulator-mvp-test.py` 从一场已传通的视频会话开始。首次权限回归先撤销专用模拟器 RECORD_AUDIO 并清除其测试拒绝历史，配对传屏后运行 `emulator-permission-test.py`；它通过真实系统弹窗拒绝/允许，验证授权前没有录音，以及拒绝后再允许能传通语音。
